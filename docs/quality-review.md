只完善质量保障，不开发产品新功能。2026-11-04 Codex连接已完成，PR #2手动审核已返回Completed、未发现重大问题；仓库自动审查开启，触发设置为每次推送。规则文件、运行配置、审核完成和用户验收是不同事件；历史结果不代替本PR最新提交检查。

## 每个PR怎样执行

1. **建立范围：**独立分支，以PR模板登记问题、复现、批准范围、MD/用户要求、预期画面与受影响模块。存在冲突先说明并等待依赖的决定；无关且获准的工作可继续。
2. **实施与本地验证：**先记录失败，再最小修复；对变更涉及的功能做针对性与旧功能回归。执行`npm ci --ignore-scripts --no-audit --no-fund`及`npm run ci`，保存提交、环境、命令、结果和未覆盖项。
3. **远程CI：**PR opened/synchronize/reopened/ready_for_review触发构建、测试、Lint三项。到Checks或Actions→PR CI查看日志，核对run.head_sha等于当前PR head；旧成功或取消/跳过均不能充当当前成功。类型检查当前不适用。
4. **审核：**Codex依据适用AGENTS.md审核差异及受影响链路。按P0/P1优先、证据、原因、影响和最小方案提出意见；已确认/可能风险/优化建议、既有/新引入问题分开。审核AI不直接改代码。
5. **有限修复：**由活动开发AI按AGENTS.md执行最多3轮；只处理低风险、明确且属于批准需求的Bug。每轮本地检查后更新PR，等新SHA的CI和Codex终态后再决定下一轮。高风险/改需求/不确定/连续无进展立即暂停审批，3轮仍有问题也暂停；计数跨对话续做累计。不得削弱测试或以新PR绕过上限。
6. **用户决定：**在聊天按【PR】【CI】【AI审核】【问题原因】【解决方案】【实际改动】【复查】【待我审批】八项简报；最终审批前更新已有日志的本PR摘要，详细过程留PR/聊天，不新建每轮报告。用户可批准/继续修改/暂缓/拒绝保留原版/要求指定回退。用户明确验证通过并同意合并后，允许Codex代为合并对应已验收PR；执行前核对批准范围、head SHA及其实际CI/审核结果，不启用GitHub自动合并。回退须说明范围和可能丢失修改并另获确认。保留PR、分支与Git检查点。CI或AI通过不代表授权；用户批准并完成合并后允许原publish.yml自动部署；须确认部署成功及公开网址确实更新，分别记录合并与上线。测试不合并、不触发正式部署。

## 首轮全面审查与后续复查

R1先固定SHA，另建不继承开发聊天的只读全仓库任务，覆盖自有产品源码、后端、内容/配置、测试/CI及适用MD、用户人工验收稿；提供执行者/链接、文件及条款覆盖表、排除项和真实交互未验证项。开发自检与独立审核分别标来源。默认PR差异Review不能代替R1，也不保证发现所有问题。PR #1/#2/#3历史工作流审核不追认为产品全面审查。

R2起重点复查本轮修改、调用/数据影响及相关回归，CI仍保留完整检查。公共样式、存储、架构或学习流程扩大时扩审；每轮绑定新SHA和终态。首轮不是修复轮，R2—R4最多对应3轮自动修复。使用稳定问题ID持续保留未解决/待复现/已修待验证/已验证解决/用户批准延期；无验证证据不能关项，差异没提到旧问题不代表消失。

每项同时说明来源、证据、M/E/P细分、用户排期、技术P0—P3、既有/新增/回归、具体版本条款及批准状态、阻断、理想状态、最小方案/风险与验证。M2/E1/P1按根因去重、跨轮不重复；疑似及争议单列待确认。用户排期P0与技术安全/数据P0不混用；“P已有规划”不等于“P0优先级”。未来版本提案不擅自变成批准。

本地`npm run ci`与GitHub独立runner是两份证据；远程CI依然执行项目现有测试，独立执行不意味着额外覆盖了用户路径。

## 完成判断

|阶段|允许作出的结论|
|---|---|
|文件已进入PR|审核规则已提交，待合并；不能声称main或后续PR已继承。|
|本地检查通过|只证明所列本机范围；不声称远程成功。|
|最新SHA三个远程job成功|当前自动检查通过；不声称产品无缺陷。|
|AI产生符合规则的实际报告|才记录AI审核跑通；配置文件存在不等于已启用。|
|用户明确体验通过/批准合并|按用户实际决定分别记录，不推导下一版授权。|

现阶段尚未配置强制分支保护、强制审核或自动验收门禁。模板复选框是人工核对，不能阻止点击合并。后续如配置硬性门禁，需明确用户决定、必需检查名称和恢复方式。

## 实际自动化能力

|步骤|当前实现及限制|
|---|---|
|PR创建/提交更新后的CI|GitHub独立runner自动运行已有build/test/lint；类型检查不适用。|
|独立Codex审核|仓库开关和每次推送触发已配置；审核异步完成。自动触发的实际证据须在对应PR记录，手动请求的结果不能冒充自动。无响应时开发AI按已授权范围手动触发并明确记录。|
|收集反馈/分类/最小修复/最多3轮|活动开发AI任务内执行；不是GitHub Actions自运行的修复机器人，无无人值守后台循环、无自动唤醒/聊天投递。任务已结束则需用户再次让开发AI继续。|
|聊天汇报|由当前任务收集并发送八项简报，未配置GitHub向Codex聊天自动推送服务。|
|发布|保留原main push自动部署，用户明确批准且完成PR合并后允许运行。既有workflow_dispatch也保留，但不得在无明确发布授权时手动运行；本轮测试不合并、不部署。|
|合并/回退|用户明确决定；风险/数据/破坏性回退必须先确认。不自动关闭PR或清理分支。|

GitHub检查红灯与“强制阻止合并”不同：本轮只验证前者，不声称已配置后者。独立AI审查无发现不能证明无Bug、规则能识别已知违规或产品验收成功。

项目只有一个专用版本日志。本机维护其“现在正在做什么”与最终PR摘要；远程PR只保留无隐私摘要。每PR记录编号、标题、分支、链接、目标、变更、CI/AI最终结果、修复轮数与处理、用户审批、已发生的合并/回退。用户决定产生前写待审批，不能从沉默推断批准。

## 怎样验证整套流程

- **本轮正向验证：**把规则/模板更新到当前CI PR的新提交，观察synchronize是否产生新run；核对head SHA和三项结果。这里不引入产品缺陷。
- **失败/更新验证：**在独立工作流PR保留首轮失败及原因，再核对更新后的新SHA绿灯。若用户明确变更需求，更新对应测试并记录替代关系，不能称之为修复产品Bug或随意弱化断言。原产品测试保持。红灯验证不代表已配置强制合并门禁。
- **AI规则验证（服务启用后）：**用一个已知违规样例、一个安全修复、一个无关改动测试能否指出有效问题、避免误报。记录规则引用、行号、影响和建议；不要预先声称审核成功。
- **真实体验验证：**选择一项用户已确认的V0.1问题，在单独修复PR中完成“复现→修复→针对检查→旧功能回归→用户验收”。页面跳动需真实浏览器几何/滚动与视频，文案需直接检查最终内容；适用手机项目仍需实体设备。

规则写法参考[OpenAI官方Code Review规则说明](https://developers.openai.com/blog/custom-code-review-rules-for-codex)：仓库级规则放根AGENTS.md，并用违规、安全和无关样例验证；规则不能取代测试和强制审批。
